The 4 Pillars of OOP

  • Encapsulation — bundle data with the behavior that acts on it; hide internals behind a clean API.
  • Abstraction — expose what, hide how. Program to interfaces, not implementations.
  • Inheritance — share behavior via is-a. Powerful but rigid — reach for it sparingly.
  • Polymorphism — one interface, many forms. Dynamic dispatch lets you swap behavior at runtime.

Modeling Building Blocks

  • Composition over inheritance — has-a beats is-a; assemble behavior from small parts.
  • Association · Aggregation · Composition — uses-a vs owns-a vs part-of (shared lifecycle).
  • Interface vs Abstract class — a capability contract vs a shared base that also holds state.
  • Enums + polymorphism — model fixed states/types cleanly instead of if/else chains.
  • Thread-safety — guard shared mutable state; call it out where it matters.
The Method · Use This Every Time

LLD is one repeatable motion. Learn it once, apply it to any problem they throw at you.

The 8-Step LLD Flow

Talk through every step out loud — interviewers score your reasoning, not just the final classes.

01

Clarify Requirements

Ask 4–6 questions. Functional scope, scale, who uses it, what varies. Never code first.

02

Define Scope

State what's in and out loud. "I'll handle X and Y, skip payments for now." Bound the problem.

03

Identify Entities

Pull the nouns → candidate classes. Vehicle, Slot, Ticket, Floor, Account.

04

Define Relationships

has-a vs is-a. Composition over inheritance. Draw associations & multiplicity.

05

Assign Behaviors

Methods on the right class. Who owns each responsibility? One reason to change each.

06

Abstract What Varies

Pricing? Allocation? Notifications? Pull into an interface + Strategy/State/Factory.

07

Walk a Core Flow

Trace one end-to-end use case through your classes to prove the design works.

08

Extend & Edge Cases

They WILL add a requirement live. Add a class/interface — never rewrite. Show Open/Closed.

SOLID — Applied

Don't name them. Show them in your class choices.

  • S Single Responsibility — one reason to change per class. Split Order from OrderPrinter.
  • O Open/Closed — add new PricingStrategy, don't edit existing. The senior-engineer signal.
  • L Liskov — a subtype must work anywhere its base does. No surprise exceptions.
  • I Interface Segregation — small focused interfaces over one fat one.
  • D Dependency Inversion — depend on interfaces, inject concretes.

Patterns That Cover 90%

Know when each one earns its place.

  • Strategy behavior varies pricing, parking-fee, payment
  • State lifecycle vending machine, order, elevator
  • Factory object creation create Vehicle/Notification by type
  • Observer notify many alerts, pub-sub, stock watchers
  • Singleton one instance config, registry — mention thread-safety
  • Decorator add-on behavior pizza toppings, coffee add-ins
  • Builder complex object assemble Pizza / Request step by step

Interview-Day Checklist
  • ✅ Ask clarifying questions before any code
  • ✅ State assumptions out loud
  • ✅ Nouns → classes, verbs → methods
  • ✅ Composition over inheritance by default
  • ✅ Pull what varies behind an interface
  • ✅ Walk one flow end-to-end
  • ✅ When they add a requirement → add a class, don't rewrite
  • ✅ Mention thread-safety where shared state exists
