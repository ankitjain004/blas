01 Requirements & Scope

Functional Requirements
  • Add expense: one person paid on behalf of several; record who paid and how much
  • Split types: equal split (everyone pays same), exact split (each person pays a precise amount), percent split (each person pays a percentage of the total)
  • View balances: "who owes whom and how much" — both per-group and globally
  • Settle up: record a payment between two users, reducing their outstanding balance
  • Simplify debts: transform a complex web of IOUs into the minimum number of transactions needed to zero all balances
Non-Functional Requirements
  • Consistent balance state — no lost updates when multiple expenses are added concurrently
  • Accurate floating-point handling — use epsilon comparisons, not == on doubles
  • Extensible split strategies — adding a new split type should not require changing existing expense logic
Clarifying Questions to Ask the Interviewer
Q: Individual or group expenses?Impacts whether we model a Group entity or just track expenses per user-pair.
Q: Multi-currency support?Needs CurrencyConversionStrategy and a base currency for balance storage.
Q: Push notifications on expense add?Suggests Observer pattern over ExpenseService.
Q: Expense history and audit trail?Immutable expense records vs. soft-delete requirement.
Q: Does "settle up" record the payment or actually move money (payment gateway)?If gateway, adds async payment state machine.
Q: Can one expense have mixed split types (person A pays exact, person B pays percent)?If yes, validation must sum heterogeneous splits.

Design principle: Split is the Strategy interface. EqualSplit, ExactSplit, and PercentSplit are concrete strategies. Expense doesn't know which strategy it holds — it just calls split.computeAmount() and split.validate() on each one. This is the Open/Closed Principle in action.

03 Strategy Pattern: Split Types

Abstract Split Base
public abstract class Split {
    protected User user;
    protected double amount; // computed share — filled by computeAmount()

    public Split(User user) {
        this.user = user;
    }

    public User getUser()   { return user; }
    public double getAmount() { return amount; }

    /**
     * Compute this user's share.
     * @param totalAmount  full expense amount
     * @param n            number of participants (used by EqualSplit)
     */
    public abstract void computeAmount(double totalAmount, int n);

    /**
     * Validate that this split is internally consistent.
     * Called with all sibling splits available so percentages/amounts can be cross-checked.
     */
    public abstract void validate(double totalAmount, List<Split> allSplits)
            throws InvalidSplitException;
}
EqualSplit
public class EqualSplit extends Split {

    public EqualSplit(User user) {
        super(user);
    }

    @Override
    public void computeAmount(double totalAmount, int n) {
        // Simple: divide total evenly
        this.amount = totalAmount / n;
    }

    @Override
    public void validate(double totalAmount, List<Split> allSplits)
            throws InvalidSplitException {
        // EqualSplit is always valid on its own; cross-sum is checked in Expense
    }
}
ExactSplit
public class ExactSplit extends Split {

    private final double exactAmount;

    public ExactSplit(User user, double exactAmount) {
        super(user);
        this.exactAmount = exactAmount;
        this.amount = exactAmount; // pre-set — no computation needed
    }

    @Override
    public void computeAmount(double totalAmount, int n) {
        // Amount is caller-provided; nothing to compute
        this.amount = exactAmount;
    }

    @Override
    public void validate(double totalAmount, List<Split> allSplits)
            throws InvalidSplitException {
        // All exact splits must sum to totalAmount (checked at Expense level)
        double sum = allSplits.stream()
                              .mapToDouble(Split::getAmount)
                              .sum();
        if (Math.abs(sum - totalAmount) > 0.01) {
            throw new InvalidSplitException(
                "ExactSplits sum=" + sum + " does not equal totalAmount=" + totalAmount);
        }
    }
}
PercentSplit
public class PercentSplit extends Split {

    private final double percent; // 0–100

    public PercentSplit(User user, double percent) {
        super(user);
        this.percent = percent;
    }

    @Override
    public void computeAmount(double totalAmount, int n) {
        this.amount = (percent / 100.0) * totalAmount;
    }

    @Override
    public void validate(double totalAmount, List<Split> allSplits)
            throws InvalidSplitException {
        double totalPercent = allSplits.stream()
                .filter(s -> s instanceof PercentSplit)
                .map(s -> (PercentSplit) s)
                .mapToDouble(ps -> ps.percent)
                .sum();
        if (Math.abs(totalPercent - 100.0) > 0.001) {
            throw new InvalidSplitException(
                "PercentSplits must sum to 100%, but got: " + totalPercent + "%");
        }
    }
}
Open/Closed Principle: To add a WeightSplit (give each person a weight ratio), you create a new class extending Split and implement computeAmount() and validate(). The Expense class, Balance class, and Group class are untouched.

04 Expense Class

Expense with Builder Pattern
public class Expense {
    private final String expenseId;
    private final User paidBy;
    private final double totalAmount;
    private final String description;
    private final List<Split> splits;
    private final LocalDateTime timestamp;

    private Expense(Builder builder) {
        this.expenseId   = builder.expenseId;
        this.paidBy      = builder.paidBy;
        this.totalAmount = builder.totalAmount;
        this.description = builder.description;
        this.splits      = new ArrayList<>(builder.splits);
        this.timestamp   = LocalDateTime.now();
    }

    public String       getExpenseId()  { return expenseId; }
    public User         getPaidBy()     { return paidBy; }
    public double       getTotalAmount(){ return totalAmount; }
    public String       getDescription(){ return description; }
    public List<Split>  getSplits()     { return Collections.unmodifiableList(splits); }
    public LocalDateTime getTimestamp() { return timestamp; }

    /**
     * Compute each split's share. Call BEFORE validateSplits().
     */
    public void computeSplitAmounts() {
        int n = splits.size();
        for (Split split : splits) {
            split.computeAmount(totalAmount, n);
        }
    }

    /**
     * Validate splits. Call AFTER computeSplitAmounts().
     * Checks: (1) each split internally valid, (2) amounts sum to totalAmount.
     */
    public void validateSplits() throws InvalidSplitException {
        for (Split split : splits) {
            split.validate(totalAmount, splits);
        }
        double computedSum = splits.stream().mapToDouble(Split::getAmount).sum();
        if (Math.abs(computedSum - totalAmount) > 0.01) {
            throw new InvalidSplitException(
                "Split amounts sum to " + computedSum
                + " but totalAmount is " + totalAmount);
        }
    }

    // ── Builder ──────────────────────────────────────────────────────
    public static class Builder {
        private String expenseId = UUID.randomUUID().toString();
        private User paidBy;
        private double totalAmount;
        private String description = "";
        private List<Split> splits = new ArrayList<>();

        public Builder paidBy(User user)         { this.paidBy = user;          return this; }
        public Builder totalAmount(double amount){ this.totalAmount = amount;   return this; }
        public Builder description(String desc)  { this.description = desc;     return this; }
        public Builder addSplit(Split split)     { this.splits.add(split);      return this; }

        public Expense build() {
            Objects.requireNonNull(paidBy,      "paidBy is required");
            if (totalAmount <= 0)
                throw new IllegalArgumentException("totalAmount must be positive");
            if (splits.isEmpty())
                throw new IllegalArgumentException("At least one split is required");
            return new Expense(this);
        }
    }

    public static Builder builder() { return new Builder(); }
}
Builder advantage: Callers chain .paidBy(alice).totalAmount(60).description("Dinner").addSplit(...) and call .build(). The build() method validates all required fields, preventing half-constructed Expense objects from entering the system.

05 Balance Tracking

Balance Class
public class Balance {
    // owes[A][B] = amount A owes B (always positive or absent)
    private final Map<String, Map<String, Double>> owes = new HashMap<>();

    /** Update owes map after a new expense is recorded. */
    public void updateBalances(Expense expense) {
        User paidBy = expense.getPaidBy();
        for (Split split : expense.getSplits()) {
            User debtor = split.getUser();
            if (debtor.getUserId().equals(paidBy.getUserId())) {
                continue; // Payer's own share doesn't create a debt
            }
            double share = split.getAmount();
            // Check if paidBy already owes debtor — net it out first
            double reverseDebt = getOwed(paidBy.getUserId(), debtor.getUserId());
            if (reverseDebt > 0) {
                if (reverseDebt >= share) {
                    // Fully offset: reduce reverse debt
                    setOwed(paidBy.getUserId(), debtor.getUserId(), reverseDebt - share);
                    continue;
                } else {
                    // Partially offset: zero reverse, record remainder forward
                    setOwed(paidBy.getUserId(), debtor.getUserId(), 0.0);
                    share -= reverseDebt;
                }
            }
            // Add remaining share to debtor→paidBy
            double existing = getOwed(debtor.getUserId(), paidBy.getUserId());
            setOwed(debtor.getUserId(), paidBy.getUserId(), existing + share);
        }
    }

    /** Record a settlement payment. */
    public void settle(String payerId, String payeeId, double amount) {
        double current = getOwed(payerId, payeeId);
        double newAmount = Math.max(0, current - amount);
        setOwed(payerId, payeeId, newAmount);
    }

    /** How much does userA owe userB? Returns 0 if no debt. */
    public double getOwed(String userAId, String userBId) {
        return owes.getOrDefault(userAId, Collections.emptyMap())
                   .getOrDefault(userBId, 0.0);
    }

    /** Net balance for a user: positive = others owe them; negative = they owe others. */
    public double getNetBalance(String userId) {
        double totalOwedToUser = owes.values().stream()
                .mapToDouble(m -> m.getOrDefault(userId, 0.0))
                .sum();
        double totalOwedByUser = owes.getOrDefault(userId, Collections.emptyMap())
                .values().stream().mapToDouble(Double::doubleValue).sum();
        return totalOwedToUser - totalOwedByUser;
    }

    /** Net balance between exactly two users.
     *  Positive = A owes B. Negative = B owes A. */
    public double getBalanceWithUser(String userAId, String userBId) {
        return getOwed(userAId, userBId) - getOwed(userBId, userAId);
    }

    /** Returns a copy of all outstanding debts (userId -> (userId -> amount)). */
    public Map<String, Map<String, Double>> getAllDebts() {
        return Collections.unmodifiableMap(owes);
    }

    private void setOwed(String fromId, String toId, double amount) {
        owes.computeIfAbsent(fromId, k -> new HashMap<>()).put(toId, amount);
    }
}
Floating-point pitfall: Never compare balance == 0.0. Use Math.abs(balance) < 0.001. Repeated additions of 60/3 = 19.999...997 accumulate error. Always use epsilon comparisons when checking if a debt is "effectively zero".

06 Debt Simplification Algorithm

Problem Statement

After 5 expenses among 4 friends you may have: Alice→Bob $20, Bob→Charlie $15, Charlie→Alice $10, Bob→Alice $5. That's 4 transactions. The simplified version: Alice→Bob $5, Charlie→Bob $5 — just 2 transactions. Goal: find the minimum number of transactions to zero all balances.

Key Insight — Proof of N-1 bound: Each transaction brings at least one person's net balance to exactly zero (the smaller side of the transaction is fully settled). N people → at most N-1 transactions to zero everyone. The greedy max-heap approach achieves this bound.This is the "minimum transactions to settle debts" classical problem — mention it by name in interviews.
Algorithm Steps
  1. Compute netBalance[user] = totalOwedToUser − totalOwedByUser for each user using the Balance map
  2. Split users into creditors (netBalance > 0, they are owed money) and debtors (netBalance < 0, they owe money)
  3. Use two max-heaps: creditors sorted by amount descending, debtors sorted by |amount| descending
  4. While both heaps non-empty: pop maxCreditor and maxDebtor, compute transaction = min(|debtor|, creditor), reduce both by transaction amount, re-insert if non-zero remainder
Full Implementation
public class DebtSimplifier {

    /**
     * Given a map of net balances (positive = owed to user, negative = user owes),
     * return the minimum list of transactions to zero all balances.
     */
    public List<Transaction> simplifyDebts(Map<User, Double> netBalances) {
        List<Transaction> result = new ArrayList<>();

        // Max-heap: creditors (most owed first)
        PriorityQueue<Map.Entry<User, Double>> creditors =
            new PriorityQueue<>((a, b) -> Double.compare(b.getValue(), a.getValue()));

        // Max-heap by absolute value: debtors (most owing first)
        PriorityQueue<Map.Entry<User, Double>> debtors =
            new PriorityQueue<>((a, b) -> Double.compare(a.getValue(), b.getValue()));

        for (Map.Entry<User, Double> entry : netBalances.entrySet()) {
            if (entry.getValue() > 0.001) {
                creditors.offer(entry);
            } else if (entry.getValue() < -0.001) {
                debtors.offer(entry);
            }
            // Near-zero balances are already settled — skip
        }

        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            Map.Entry<User, Double> creditor = creditors.poll();
            Map.Entry<User, Double> debtor   = debtors.poll();

            double amount = Math.min(creditor.getValue(), -debtor.getValue());

            result.add(new Transaction(debtor.getKey(), creditor.getKey(), amount));

            double creditorRemainder = creditor.getValue() - amount;
            double debtorRemainder   = debtor.getValue()   + amount; // becomes less negative

            if (creditorRemainder > 0.001) {
                creditors.offer(Map.entry(creditor.getKey(), creditorRemainder));
            }
            if (debtorRemainder < -0.001) {
                debtors.offer(Map.entry(debtor.getKey(), debtorRemainder));
            }
        }

        return result;
    }

    /**
     * Convenience: compute net balances from a Balance object, then simplify.
     */
    public List<Transaction> simplifyGroupDebts(List<User> members, Balance balance) {
        Map<User, Double> netBalances = new HashMap<>();
        for (User member : members) {
            netBalances.put(member, balance.getNetBalance(member.getUserId()));
        }
        return simplifyDebts(netBalances);
    }
}
Worked Example
Net balances BEFORE simplification:
  Alice:   +$15  (others owe her $15 net)
  Bob:     -$5   (he owes $5 net)
  Charlie: -$10  (he owes $10 net)

Heaps:
  creditors: [Alice +15]
  debtors:   [Charlie -10, Bob -5]

Step 1: creditor=Alice(+15), debtor=Charlie(-10)
  amount = min(15, 10) = $10
  → Transaction: Charlie pays Alice $10
  creditorRemainder = 15-10 = 5  → re-insert Alice(+5)
  debtorRemainder   = -10+10 = 0 → discard Charlie

Step 2: creditor=Alice(+5), debtor=Bob(-5)
  amount = min(5, 5) = $5
  → Transaction: Bob pays Alice $5
  creditorRemainder = 0 → discard
  debtorRemainder   = 0 → discard

Result: 2 transactions (was potentially 4+ raw IOUs)

07 Group Management

public class Group {
    private final String groupId;
    private final String name;
    private final List<User> members    = new ArrayList<>();
    private final List<Expense> expenses = new ArrayList<>();
    private final Balance groupBalance   = new Balance();
    private final DebtSimplifier simplifier = new DebtSimplifier();

    public Group(String groupId, String name) {
        this.groupId = groupId;
        this.name    = name;
    }

    public void addMember(User user) {
        if (!members.contains(user)) {
            members.add(user);
        }
    }

    /**
     * Remove member only if they have no pending balances.
     */
    public void removeMember(User user) throws IllegalStateException {
        double net = groupBalance.getNetBalance(user.getUserId());
        if (Math.abs(net) > 0.01) {
            throw new IllegalStateException(
                user.getName() + " has outstanding balance of " + net
                + ". Settle before removing.");
        }
        members.remove(user);
    }

    /**
     * Thread-safe expense addition. Compute amounts and validate before recording.
     */
    public synchronized void addExpense(Expense expense) {
        expense.computeSplitAmounts();
        expense.validateSplits();
        expenses.add(expense);
        groupBalance.updateBalances(expense);
    }

    public Balance getGroupBalance() {
        return groupBalance;
    }

    public double getMemberNetBalance(User user) {
        return groupBalance.getNetBalance(user.getUserId());
    }

    public List<Transaction> getSimplifiedSettlements() {
        return simplifier.simplifyGroupDebts(members, groupBalance);
    }

    public List<Expense> getExpenses() {
        return Collections.unmodifiableList(expenses);
    }

    public List<User> getMembers() {
        return Collections.unmodifiableList(members);
    }

    public String getGroupId() { return groupId; }
    public String getName()    { return name; }
}
Encapsulation: getExpenses() returns an unmodifiable view. Callers cannot directly mutate the expenses list — they must use addExpense() which applies validation and balance updates atomically.

08 Concurrency

The Race Condition Scenario

Alice and Bob both add expenses to the same group at the same instant. Without synchronization:

Thread A (Alice's expense)          Thread B (Bob's expense)
───────────────────────────         ─────────────────────────
1. expense.computeSplitAmounts()    1. expense.computeSplitAmounts()
2. groupBalance.updateBalances()    2. groupBalance.updateBalances()
   reads owes["charlie"]["alice"]      reads owes["charlie"]["alice"]  ← BOTH read 0.0
   computes 0.0 + 20 = 20             computes 0.0 + 15 = 15
   writes owes["charlie"]["alice"]=20  writes owes["charlie"]["alice"]=15  ← LOST $20!
ConcurrentHashMap alone is insufficient. It protects individual key reads/writes but a compound read → compute → write is still a race. Thread A reads 0, Thread B reads 0, both compute independently, one write clobbers the other. You need synchronization at the addExpense level.
Solutions
MechanismApplied ToGuarantees
synchronized on addExpense()Group classOnly one expense added at a time; read-modify-write is atomic
AtomicLong for expense IDExpenseServiceThread-safe sequential ID generation without synchronization overhead
ConcurrentHashMap for owesBalanceSafe concurrent reads; still need synchronized on writes
Immutable Expense after buildExpense classNo mutable shared state once built — safe to read from multiple threads
 
// Thread-safe expense addition in Group.java
public synchronized void addExpense(Expense expense) {
    expense.computeSplitAmounts();  // idempotent — safe to call once
    expense.validateSplits();       // throws InvalidSplitException if bad
    expenses.add(expense);          // CopyOnWriteArrayList alternative for reads
    groupBalance.updateBalances(expense); // the critical compound operation
}

// Thread-safe ID generation in ExpenseService.java
private final AtomicLong expenseIdCounter = new AtomicLong(0);

public String generateExpenseId() {
    return "EXP-" + expenseIdCounter.incrementAndGet();
}
Read-heavy optimization: If reads vastly outnumber writes (typical in a real app where users view balances often but add expenses rarely), replace synchronized with ReadWriteLock: shared read lock for getGroupBalance(), exclusive write lock for addExpense().

09 Walking a Flow

Setup: Three Friends, Two Expenses
Users: Alice (A), Bob (B), Charlie (C)
Group: "Weekend Trip"
Starting balance: all zero
Expense 1: Alice pays $60 for dinner (equal split among all 3)
  1. Caller builds expense:
    Expense dinner = Expense.builder().paidBy(alice).totalAmount(60).description("Dinner").addSplit(new EqualSplit(alice)).addSplit(new EqualSplit(bob)).addSplit(new EqualSplit(charlie)).build();
  2. group.addExpense(dinner) acquires synchronized lock
  3. dinner.computeSplitAmounts(): each EqualSplit.computeAmount(60, 3) → amount = 60/3 = $20 each
  4. dinner.validateSplits(): sum = 20+20+20 = 60 ✓
  5. groupBalance.updateBalances(dinner):
    • Alice's split: paidBy==split.user → skip (she paid, her own share covered)
    • Bob's split: Bob owes Alice $20 → owes[bob][alice] = 20
    • Charlie's split: Charlie owes Alice $20 → owes[charlie][alice] = 20
Balance state after Expense 1:
  Bob    → Alice :  $20
  Charlie → Alice:  $20
Expense 2: Bob pays $30 for taxi (Alice and Bob split equally = $15 each)
  1. Caller builds expense:
    Expense taxi = Expense.builder().paidBy(bob).totalAmount(30).description("Taxi").addSplit(new EqualSplit(alice)).addSplit(new EqualSplit(bob)).build();
  2. taxi.computeSplitAmounts(): each share = 30/2 = $15
  3. groupBalance.updateBalances(taxi):
    • Bob's split: paidBy==split.user → skip
    • Alice's split: Alice owes Bob $15. But check reverse: does Bob owe Alice? Yes, $20! Reverse debt $20 ≥ $15 → net it out: reduce owes[bob][alice] from $20 to $5. Alice's forward debt zeroed.
Balance state after Expense 2 (automatically netted):
  Bob     → Alice :  $5    (was $20, reduced by $15)
  Charlie → Alice :  $20   (unchanged)

Simplified settlements (same as raw here — already minimal):
  Bob     pays Alice  $5
  Charlie pays Alice  $20

10 Extensions

Multi-Currency Support
CurrencyConversionStrategy: Interface with double convert(double amount, Currency from, Currency to). FixedRateConverter for tests, ExchangeRateAPIConverter for production.Expense stores its Currency. Balance always stores in base currency (e.g., USD). On updateBalances, convert split.getAmount() from expense.getCurrency() to base before storing.
Expense Notifications (Observer)
public interface ExpenseObserver {
    void onExpenseAdded(Expense expense, Group group);
    void onSettlementDone(String payerId, String payeeId, double amount);
}

// In Group:
private final List<ExpenseObserver> observers = new ArrayList<>();

public void addObserver(ExpenseObserver observer) { observers.add(observer); }

public synchronized void addExpense(Expense expense) {
    expense.computeSplitAmounts();
    expense.validateSplits();
    expenses.add(expense);
    groupBalance.updateBalances(expense);
    observers.forEach(o -> o.onExpenseAdded(expense, this)); // notify AFTER commit
}
Expense Categories
Category enum: FOOD, TRANSPORT, RENT, ENTERTAINMENT, UTILITIES, OTHER. Add Category category field to Expense. Group can then provide getExpensesByCategory(Category) for analytics.
Recurring Expenses
RecurringExpense: Wraps an Expense template with a RecurrenceRule (DAILY/WEEKLY/MONTHLY) and nextDueDate. A ScheduledExecutorService checks daily and auto-creates expenses when nextDueDate is reached.E.g., shared Netflix subscription billed monthly to the group.
Pluggable Debt Simplification
public interface DebtSimplificationStrategy {

public class GreedySimplification implements DebtSimplificationStrategy { /* max-heap */ }
public class MinCostFlowSimplification implements DebtSimplificationStrategy { /* exact optimal */ }

// ExpenseService accepts strategy via constructor injection
public class ExpenseService {
    private final DebtSimplificationStrategy simplificationStrategy;
    public ExpenseService(DebtSimplificationStrategy strategy) {
        this.simplificationStrategy = strategy;
    }
}

11 Interview Talking Points

On Strategy Pattern (OCP): "Strategy for split types means adding PercentageSplit requires zero changes to Expense class — that's the Open/Closed Principle. I just create a new Split subclass, implement computeAmount() and validate(), and the Expense class polymorphically calls it without knowing the concrete type."
On Debt Simplification: "The greedy algorithm guarantees at most N-1 transactions for N people. The proof: each step of the algorithm eliminates at least one person from the debt graph because the smaller side of the transaction reaches exactly zero. So N people → N-1 steps maximum."
On Concurrency: "ConcurrentHashMap alone isn't enough for balance updates. It protects individual key reads/writes, but updateBalances() is a compound read-modify-write — I read the old balance, add the new amount, then write back. Two concurrent calls can both read 0, both compute independently, and one write clobbers the other. I need synchronized on addExpense() to make the entire operation atomic."
On Builder Pattern: "Builder on Expense lets callers set paidBy, amount, and description fluently, then validates all required fields in build(). This prevents partially constructed Expense objects from entering the system — you either build a valid Expense or throw an exception."
On Observer Pattern: "For notifications I'd use Observer — Group holds a list of ExpenseObservers and notifies them after each addExpense. Email notification, push notification, and UI refresh all subscribe independently. Adding WhatsApp notifications later means implementing ExpenseObserver once, zero changes to Group."
