01 Requirements & Scope

Functional Requirements
  • Insert coin/note — machine accepts monetary input incrementally; running total is tracked.
  • Select product by code — user enters product code (e.g., "C01") after inserting money.
  • Dispense product — machine physically releases the product once payment is validated.
  • Return change — any overpayment is returned as coins using a greedy algorithm.
  • Cancel transaction — user can cancel at any time; all inserted money is returned.
  • Show out-of-stock — if product quantity is 0, machine declines selection and prompts user.
Machine States
StateDescriptionValid Actions
IdleStateWaiting for first coin. Default state on startup.insertCoin
HasMoneyStateMoney inserted; awaiting product selection.insertCoin, selectProduct, cancel
DispensingStateProduct selected and validated; dispensing in progress.dispense (internal)
OutOfStockStateRequested product is unavailable.restock (admin only)
Clarifying Questions
QuestionWhy it mattersReasonable default
Coins only, or notes too?Affects Payment model — notes have larger denominations.Coins only for now; add Note enum as extension.
Can a user buy multiple products in one transaction?Affects whether DispensingState loops or returns to Idle between items.One product per transaction; mention multi-purchase as extension.
Can admin restock remotely?Implies an AdminState with elevated privileges.Local restock only; add AdminState as extension.
Is exact change required?If machine runs out of change coins, can it still accept overpayment?Machine always has change; throw exception if change not available.
What if machine jams mid-dispense?Implies a JammedState and a recovery flow.Out of scope; mention as production concern.
Interviewer signal: Opening with state identification — not class names — shows you recognize this as a behavioral problem, not just a data model. Say: "I see 4 states. Let me define the state machine before writing any classes."

State Pattern — a behavioral pattern where an object's behavior changes based on its internal state. The object appears to change its class. Gang of Four, Design Patterns (1994) — the textbook definition your interviewer may quote.

03 State Pattern Deep Dive

The Problem Without State Pattern
// ❌ WITHOUT State Pattern — this is what NOT to do
public class VendingMachineBAD {
    private enum MachineState { IDLE, HAS_MONEY, DISPENSING, OUT_OF_STOCK }
    private MachineState state = MachineState.IDLE;

    public void insertCoin(Coin coin) {
        if (state == MachineState.IDLE) {
            payment.addCoin(coin);
            state = MachineState.HAS_MONEY;
        } else if (state == MachineState.HAS_MONEY) {
            payment.addCoin(coin);
        } else if (state == MachineState.DISPENSING) {
            System.out.println("Cannot insert coin while dispensing");
        } else if (state == MachineState.OUT_OF_STOCK) {
            System.out.println("Machine out of stock");
        }
    }

    public void selectProduct(String code) {
        if (state == MachineState.IDLE) {
            System.out.println("Insert coins first");
        } else if (state == MachineState.HAS_MONEY) {
            // check stock, check funds, transition...
        } else if (state == MachineState.DISPENSING) {
            System.out.println("Already dispensing");
        } else if (state == MachineState.OUT_OF_STOCK) {
            System.out.println("Out of stock");
        }
    }
    // dispense(), cancel() — same 4-branch if-else each.
    // 4 methods × 4 states = 16 branches.
    // Add MaintenanceState → touch ALL 4 methods → violates OCP.
}
The proliferation problem: With 4 states and 4 actions you have 16 branches. Add a 5th state (Maintenance, Jammed, CardPayment) and you must open every single method. This is the classic symptom that screams "State Pattern needed."
The Solution: State as First-Class Class
// ✅ WITH State Pattern — each state class handles its own branches
// IdleState only has logic for what Idle does. Zero HAS_MONEY logic here.
public class IdleState implements State {

    @Override
    public void insertCoin(VendingMachine machine, Coin coin) {
        machine.getCurrentPayment().addCoin(coin);
        System.out.printf("[Idle→HasMoney] Inserted %s. Total: $%.2f%n",
                coin, machine.getCurrentPayment().getTotal());
        machine.setCurrentState(machine.getHasMoneyState());
    }

    @Override
    public void selectProduct(VendingMachine machine, String productCode) {
        throw new InvalidStateTransitionException("Insert coins before selecting a product.");
    }

    @Override
    public void dispense(VendingMachine machine) {
        throw new InvalidStateTransitionException("Nothing to dispense in Idle state.");
    }

    @Override
    public void cancel(VendingMachine machine) {
        System.out.println("[Idle] Nothing to cancel.");
        // No-op — no money inserted yet
    }
}
// Adding MaintenanceState? Create MaintenanceState.java.
// IdleState, HasMoneyState, DispensingState, OutOfStockState — ZERO changes.
The key insight to verbalize: "Each state class has one reason to change — when the business rules for that state change. IdleState changes when 'idle behavior' changes. No cross-state contamination. That is Single Responsibility applied to state machine design."

HasMoneyState
public class HasMoneyState implements State {

    @Override
    public void insertCoin(VendingMachine machine, Coin coin) {
        machine.getCurrentPayment().addCoin(coin);
        System.out.printf("[HasMoney] %s inserted. Running total: $%.2f%n",
                coin.name(), machine.getCurrentPayment().getTotal());
        // Stays in HasMoneyState
    }

    @Override
    public void selectProduct(VendingMachine machine, String productCode) {
        Inventory inventory = machine.getInventory();

        // Guard: out of stock?
        if (!inventory.isAvailable(productCode)) {
            System.out.printf("[HasMoney] Product %s is out of stock.%n", productCode);
            machine.setCurrentState(machine.getOutOfStockState());
            return;
        }

        Product product = inventory.getProduct(productCode);

        // Guard: insufficient funds?
        double total = machine.getCurrentPayment().getTotal();
        if (total < product.getPrice()) {
            throw new InsufficientFundsException(product.getPrice(), total);
        }

        // All checks passed — transition to dispensing
        machine.setSelectedProduct(product);
        machine.setCurrentState(machine.getDispensingState());
        System.out.printf("[HasMoney→Dispensing] Selected: %s ($%.2f). Paid: $%.2f%n",
                product.getName(), product.getPrice(), total);
        machine.dispense();   // trigger dispense immediately
    }

    @Override
    public void dispense(VendingMachine machine) {
        throw new InvalidStateTransitionException(
                "Select a product before dispensing.");
    }

    @Override
    public void cancel(VendingMachine machine) {
        double refund = machine.getCurrentPayment().getTotal();
        machine.resetPayment();
        machine.setCurrentState(machine.getIdleState());
        System.out.printf("[HasMoney→Idle] Transaction cancelled. Refunding $%.2f%n", refund);
    }
}
DispensingState
public class DispensingState implements State {

    @Override
    public void insertCoin(VendingMachine machine, Coin coin) {
        throw new InvalidStateTransitionException(
                "Cannot insert coins: dispensing in progress.");
    }

    @Override
    public void selectProduct(VendingMachine machine, String productCode) {
        throw new InvalidStateTransitionException(
                "Already dispensing — wait for current transaction to complete.");
    }

    @Override
    public void dispense(VendingMachine machine) {
        Product product = machine.getSelectedProduct();
        Inventory inventory = machine.getInventory();

        // Atomically decrement inventory
        inventory.removeProduct(product.getProductCode(), 1);

        // Calculate and return change
        double paid   = machine.getCurrentPayment().getTotal();
        double change = paid - product.getPrice();
        if (change > 0.001) {
            // Return change as coins
            machine.returnChange(change);
            System.out.printf("[Dispensing] Returning change: $%.2f%n", change);
        }

        System.out.printf("[Dispensing] 🎉 Dispensing: %s. Enjoy!%n", product.getName());

        // Reset state for next customer
        machine.resetPayment();
        machine.setSelectedProduct(null);
        machine.setCurrentState(machine.getIdleState());
        System.out.println("[Dispensing→Idle] Ready for next customer.");
    }

    @Override
    public void cancel(VendingMachine machine) {
        throw new InvalidStateTransitionException(
                "Cannot cancel: dispensing already in progress.");
    }
}
OutOfStockState
public class OutOfStockState implements State {

    @Override
    public void insertCoin(VendingMachine machine, Coin coin) {
        throw new OutOfStockException("machine");
    }

    @Override
    public void selectProduct(VendingMachine machine, String productCode) {
        throw new OutOfStockException(productCode);
    }

    @Override
    public void dispense(VendingMachine machine) {
        throw new OutOfStockException("machine");
    }

    @Override
    public void cancel(VendingMachine machine) {
        // Allow cancel even in OOS — return any money the user inserted
        double refund = machine.getCurrentPayment().getTotal();
        if (refund > 0) {
            machine.resetPayment();
            System.out.printf("[OutOfStock] Refunding $%.2f.%n", refund);
        }
        machine.setCurrentState(machine.getIdleState());
    }

    /**
     * Called by an admin or automated restock service.
     * Transitions machine back to Idle after restocking.
     */
    public void restock(VendingMachine machine, String productCode, int quantity) {
        machine.getInventory().addStock(productCode, quantity);
        machine.setCurrentState(machine.getIdleState());
        System.out.printf("[OutOfStock→Idle] Restocked %s × %d.%n", productCode, quantity);
    }
}

05 VendingMachine Class

The Context Class: VendingMachine does not know how to handle any action. It only knows which state it's in, and it delegates everything to that state. States hold behavior; the context holds data. This is SRP expressed architecturally. 
import java.util.List;

public class VendingMachine {

    // ── State instances (all pre-created, reused) ──────────────────────────────
    private final IdleState        idleState        = new IdleState();
    private final HasMoneyState    hasMoneyState    = new HasMoneyState();
    private final DispensingState  dispensingState  = new DispensingState();
    private final OutOfStockState  outOfStockState  = new OutOfStockState();

    // ── Current state ──────────────────────────────────────────────────────────
    private State currentState;

    // ── Data ───────────────────────────────────────────────────────────────────
    private final Inventory inventory;
    private Payment currentPayment;
    private Product selectedProduct;

    // ── Constructor ────────────────────────────────────────────────────────────
    public VendingMachine(Inventory inventory) {
        this.inventory      = inventory;
        this.currentPayment = new Payment();
        this.currentState   = idleState;   // machine starts idle
    }

    // ── Public API — all delegated to currentState ─────────────────────────────

    public void insertCoin(Coin coin) {
        currentState.insertCoin(this, coin);
    }

    public void selectProduct(String productCode) {
        currentState.selectProduct(this, productCode);
    }

    public void dispense() {
        currentState.dispense(this);
    }

    public void cancel() {
        currentState.cancel(this);
    }

    // ── Internal helpers called by State implementations ───────────────────────

    public void returnChange(double amount) {
        List<Coin> change = ChangeCalculator.calculate(amount);
        System.out.print("[Change] Returning: ");
        change.forEach(c -> System.out.print(c.name() + " "));
        System.out.println();
    }

    public void resetPayment() {
        this.currentPayment = new Payment();
    }

    // ── Getters / Setters for state transitions ────────────────────────────────

    public void    setCurrentState(State state)    { this.currentState = state; }
    public State   getCurrentState()               { return currentState; }

    public IdleState       getIdleState()          { return idleState; }
    public HasMoneyState   getHasMoneyState()      { return hasMoneyState; }
    public DispensingState getDispensingState()    { return dispensingState; }
    public OutOfStockState getOutOfStockState()    { return outOfStockState; }

    public Inventory getInventory()                { return inventory; }
    public Payment   getCurrentPayment()           { return currentPayment; }

    public Product   getSelectedProduct()          { return selectedProduct; }
    public void      setSelectedProduct(Product p) { this.selectedProduct = p; }

    public String getCurrentStateName() {
        return currentState.getClass().getSimpleName();
    }
}
Why pre-create all State instances? States are stateless — they hold no data of their own. All data lives in VendingMachine. Pre-creating them avoids allocating a new object on every transition, and lets states be singletons within the machine lifecycle. This is the standard State Pattern implementation from GoF.

Inventory — with synchronized removeProduct for concurrency safety
import java.util.HashMap;
import java.util.Map;

public class Inventory {
    private final Map<String, Product> products = new HashMap<>();
    private final Map<String, Integer> stock     = new HashMap<>();

    public synchronized void addProduct(Product product, int quantity) {
        products.put(product.getProductCode(), product);
        stock.merge(product.getProductCode(), quantity, Integer::sum);
        System.out.printf("[Inventory] Added %s × %d%n", product.getName(), quantity);
    }

    public synchronized void addStock(String productCode, int quantity) {
        if (!products.containsKey(productCode)) {
            throw new IllegalArgumentException("Unknown product: " + productCode);
        }
        stock.merge(productCode, quantity, Integer::sum);
    }

    /**
     * Thread-safe decrement. Synchronized to prevent two buyers
     * simultaneously reading qty=1 and both proceeding to dispense.
     *
     * @throws IllegalStateException if stock goes to 0
     */
    public synchronized void removeProduct(String productCode, int quantity) {
        Integer current = stock.get(productCode);
        if (current == null || current < quantity) {
            throw new OutOfStockException(productCode);
        }
        stock.put(productCode, current - quantity);
        System.out.printf("[Inventory] %s: qty %d → %d%n",
                productCode, current, current - quantity);
    }

    public synchronized boolean isAvailable(String productCode) {
        return stock.getOrDefault(productCode, 0) > 0;
    }

    public Product getProduct(String productCode) {
        Product p = products.get(productCode);
        if (p == null) throw new IllegalArgumentException("Product not found: " + productCode);
        return p;
    }

    public synchronized int getStock(String productCode) {
        return stock.getOrDefault(productCode, 0);
    }
}
Race condition without synchronization: Two users simultaneously select the last Coke. Both call isAvailable() and both see qty=1. Both proceed to removeProduct(). First decrements to 0. Second tries to decrement 0 → would go to -1 without the guard. synchronized on removeProduct ensures only one thread at a time decrements, and the guard current < quantity rejects the second.

ChangeCalculator — greedy largest-coin-first algorithm
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class ChangeCalculator {

    // Coins in descending order for greedy selection
    private static final List<Coin> COINS_DESC = Arrays.asList(
            Coin.ONE_DOLLAR,
            Coin.QUARTER,
            Coin.DIME,
            Coin.NICKEL,
            Coin.PENNY
    );

    /**
     * Returns the fewest coins totaling 'amount' using greedy selection.
     * Uses integer arithmetic (cents) to avoid floating-point drift.
     *
     * @param amount  change amount in dollars (e.g., 0.75)
     * @return        list of Coin denominations to return
     */
    public static List<Coin> calculate(double amount) {
        List<Coin> result    = new ArrayList<>();
        // Convert to cents to avoid floating-point precision issues
        int remaining = (int) Math.round(amount * 100);

        for (Coin coin : COINS_DESC) {
            int coinCents = (int) Math.round(coin.getValue() * 100);
            while (remaining >= coinCents) {
                result.add(coin);
                remaining -= coinCents;
            }
        }

        if (remaining > 0) {
            // In production: alert operator that exact change is not possible
            System.out.printf("[ChangeCalculator] WARNING: Cannot make exact change." +
                    " Remaining: %d cents%n", remaining);
        }

        return result;
    }

    /**
     * Validates that the machine can make the required change
     * (simplified — production tracks machine's coin inventory).
     */
    public static boolean canMakeChange(double amount) {
        return calculate(amount).stream()
                .mapToDouble(Coin::getValue)
                .sum() >= amount - 0.001;
    }
}
Why integer arithmetic for cents? 0.1 + 0.2 == 0.30000000000000004 in IEEE 754 floating-point. Multiplying by 100 and working in integer cents avoids accumulation of rounding errors that would produce wrong change amounts.

08 Concurrency

The State Transition Race Condition
Thread 1 (User A in HasMoneyState)        Thread 2 (User B — cancel button)
──────────────────────────────            ──────────────────────────────
checks: state == HasMoney ✓               cancel() called
selectProduct("C01") —                    cancel() transitions → IdleState
         ↓                                        ↓
continues executing as                    payment reset, state = Idle
"HasMoneyState.selectProduct"             
calls inventory.removeProduct()           ← product removed from Idle state!
calls machine.dispense()                  ← machine now in Idle but dispensing!

                  ↑ INVALID STATE after concurrent cancel
Solution: synchronized state transition block
// In VendingMachine — make state-changing operations synchronized
public synchronized void insertCoin(Coin coin) {
    currentState.insertCoin(this, coin);
}

public synchronized void selectProduct(String productCode) {
    currentState.selectProduct(this, productCode);
}

public synchronized void dispense() {
    currentState.dispense(this);
}

public synchronized void cancel() {
    currentState.cancel(this);
}
// Each public action is synchronized on the VendingMachine instance.
// Only one action can execute at a time — serialized state transitions.
Alternative: ReentrantLock with tryLock() for responsive cancellation
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.TimeUnit;

public class VendingMachineConcurrent {
    private final ReentrantLock stateLock = new ReentrantLock();

    public boolean insertCoin(Coin coin, long timeoutMs) throws InterruptedException {
        if (stateLock.tryLock(timeoutMs, TimeUnit.MILLISECONDS)) {
            try {
                currentState.insertCoin(this, coin);
                return true;
            } finally {
                stateLock.unlock();
            }
        }
        System.out.println("Machine busy — please wait.");
        return false;
    }

    /**
     * Cancel with immediate attempt — don't wait forever.
     * If lock is held, the user pressed cancel at the exact same time
     * as another action. Try once and give up gracefully.
     */
    public boolean cancel() {
        if (stateLock.tryLock()) {
            try {
                currentState.cancel(this);
                return true;
            } finally {
                stateLock.unlock();
            }
        }
        System.out.println("Cannot cancel right now — operation in progress.");
        return false;
    }
}
Inventory vs Machine Lock: Note that Inventory.removeProduct() has its own synchronized — it guards the stock count. The machine-level lock guards state transitions. These are two different locks at two different granularities, which is correct and intentional.
Deadlock risk: If you hold the machine lock and try to acquire the inventory lock, and another thread holds the inventory lock trying to acquire the machine lock — deadlock. Avoid this by always acquiring locks in the same order, or by using a single lock that covers both.

09 Walking a Flow

Complete Transaction: User buys a Coke for $0.75
  1. Initial state: Machine in IdleState. Inventory: Coke (C01, $0.75) qty=5, Chips (P02, $1.25) qty=3.
  2. User inserts QUARTER ($0.25) → machine.insertCoin(QUARTER) → IdleState.insertCoin(machine, QUARTER)
        → payment.addCoin(QUARTER) → totalInserted=$0.25
        → machine.setCurrentState(hasMoneyState)
        → Console: "[Idle→HasMoney] QUARTER inserted. Total: $0.25"
  3. User inserts second QUARTER → machine.insertCoin(QUARTER) → HasMoneyState.insertCoin
        → totalInserted=$0.50. Stays in HasMoneyState.
  4. User inserts third QUARTER → totalInserted=$0.75. Stays in HasMoneyState.
  5. User selects C01 → machine.selectProduct("C01") → HasMoneyState.selectProduct(machine, "C01")
        → inventory.isAvailable("C01") → true (qty=5)
        → product.getPrice()=$0.75. totalInserted=$0.75 >= 0.75 → OK
        → machine.setSelectedProduct(coke)
        → machine.setCurrentState(dispensingState)
        → machine.dispense() triggered immediately
  6. DispensingState.dispense(machine):
        → inventory.removeProduct("C01", 1) → synchronized → qty: 5→4
        → change = $0.75 - $0.75 = $0.00 → no change to return
        → Console: "[Dispensing] 🎉 Dispensing: Coke. Enjoy!"
        → machine.resetPayment() → new Payment()
        → machine.setSelectedProduct(null)
        → machine.setCurrentState(idleState)
        → Console: "[Dispensing→Idle] Ready for next customer."
  7. Final state: Machine in IdleState. Coke qty=4. Payment cleared.

10 Extensions

Card Payment — State + Strategy combination
  • Add PaymentMethod interface: boolean processPayment(double amount), boolean refund(double amount).
  • Implement CoinPayment implements PaymentMethod (current logic) and CardPayment implements PaymentMethod (calls card terminal API).
  • Add CardPaymentState implements State: insertCoin() → "card payment in progress"; selectProduct() → charges card then transitions to Dispensing.
  • Zero changes to IdleState, HasMoneyState, DispensingState.
public interface PaymentMethod {
    boolean processPayment(double amount);
    boolean refund(double amount);
    double getBalance();
}

public class CardPayment implements PaymentMethod {
    private final String cardToken;

    public CardPayment(String cardToken) {
        this.cardToken = cardToken;
    }

    @Override
    public boolean processPayment(double amount) {
        // In production: call card terminal SDK
        System.out.printf("[Card] Charged $%.2f to card ending %s%n",
                amount, cardToken.substring(cardToken.length() - 4));
        return true;
    }

    @Override
    public boolean refund(double amount) {
        System.out.printf("[Card] Refunded $%.2f to card%n", amount);
        return true;
    }

    @Override
    public double getBalance() {
        return Double.MAX_VALUE;   // card has no pre-defined limit for vending
    }
}
Temperature Zones — Decorator on Product
  • Add TemperatureZone enum: AMBIENT, REFRIGERATED, FROZEN.
  • TemperatureControlledProduct extends Product: adds TemperatureZone zone field.
  • Inventory groups products by zone; each zone has its own dispenser motor.

Remote Admin Console — AdminState
  • Add AdminState implements State. Admin actions: restock, price change, clear jams.
  • VendingMachine.enterAdminMode(String adminPin) validates PIN and transitions to AdminState.
  • All regular user actions throw InvalidStateTransitionException in AdminState.
The pattern holds for every extension: Adding CardPayment created CardPaymentState and CardPayment. Zero modifications to the four existing state classes. This is the Open/Closed Principle playing out exactly as intended with the State Pattern.

11 Interview Talking Points

Five Lines That Show Senior Depth
1. On why State Pattern "State pattern eliminates a 4×4=16 branch if-else matrix. Each state class handles exactly its valid transitions and throws InvalidStateTransitionException for invalid ones — this is how I enforce the state machine contract, not just silently ignore invalid inputs."
2. On exception design "I chose to throw InvalidStateTransitionException instead of silently ignoring invalid actions. Silent failures hide bugs. An exception surfaces the violated contract immediately in tests and in production logs."
3. On SRP split "The context class, VendingMachine, holds all mutable data — payment, selected product, inventory. State classes are stateless — they only hold a reference to the context. This SRP split means states can be singletons and never need to be re-created."
4. On inventory concurrency "Inventory.removeProduct is synchronized because it is a compound operation: read stock, check > 0, decrement. Without synchronization, two buyers could both pass the check on qty=1 and both dispense — negative stock. The synchronized keyword makes this check-then-act atomic."
5. On adding a 5th state "To add a Maintenance state, I create MaintenanceState implements State. It throws InvalidStateTransitionException on all user actions. I add enterMaintenance() and exitMaintenance() to VendingMachine. The four existing state classes — Idle, HasMoney, Dispensing, OutOfStock — are never touched."
Bonus point getter: "I use integer arithmetic (cents) in ChangeCalculator to avoid IEEE 754 floating-point errors. 0.1 + 0.2 != 0.3 in Java. For any financial calculation, convert to the smallest currency unit as an integer, compute, then divide back. This is how payment processors work in production."
